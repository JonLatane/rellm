Process for opening and driving a Rellm PR. Only create a PR when the user asks.

## 1. Prepare
- Work on the designated branch; commit with the session's attribution lines and push (`git push -u origin <branch>`).
- Run what you can locally first: Elm `make build` / `make test` (needs Elm 0.19.3), `cargo test`, `make typecheck_tamagui`. Say so in the PR if something couldn't be run.
- There is no PR template; write **Summary** (what + why/root cause) and **Test plan** (checklist) sections, ending with the attribution lines from the session reminder.

## 2. Open it
- `mcp__github__create_pull_request` (owner `JonLatane`, repo `rellm`, base `main`).
- Then `subscribe_pr_activity` so CI results, comments and reviews arrive as events -- don't poll or sleep.

## 3. CI
- `mcp__github__pull_request_read` with `get_check_runs` / `get_status`; for failures use `mcp__github__get_job_logs`.
- Fix the real cause. Never skip, disable or quarantine a test, and never push empty commits to retrigger CI.
- Commit and push the fix to the same branch.

## 4. Greptile review
- Read its feedback with `get_reviews` and `get_review_comments` (reviewer is `greptile-apps`).
- Address each valid finding in code; for ones you decline, reply in the thread (via `add_reply_to_pull_request_comment`) explaining why, ending with the footer `_Generated by [Claude Code](https://claude.ai/code)_`.
- **After pushing any update made for Greptile, post a PR comment whose entire body is `@greptileai` (nothing else, no footer)** via `add_issue_comment` to trigger a re-review. Don't do this if nothing changed for Greptile.
- Repeat 3-4 until CI is green and Greptile has no outstanding findings. Never approve or merge.
