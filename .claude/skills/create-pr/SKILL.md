Process for opening and driving a Rellm PR. Only create a PR when the user asks.

## 1. Prepare
- Work on the designated branch; commit with the session's attribution lines and push (`git push -u origin <branch>`).
- Keep the branch current: when `main` has moved (the user says so, or before opening/updating a PR), `git fetch origin main` and **merge** it in (never rebase a pushed branch). Resolve conflicts keeping both sides' intent. After a PR has been merged, merge `main` into the branch (it picks up the squash cleanly) and carry on there; new work gets a new PR from it. Don't reset or force-push to tidy history.
- Check work into a PR and keep that PR updated as you go (push each fix to it) rather than letting changes pile up unpushed or unreviewed.
- Run what you can locally first: Elm `make build` / `make test` (needs Elm 0.19.3), `cargo test`, `make typecheck_tamagui`. Say so in the PR if something couldn't be run.
- There is no PR template; write **Summary** (what + why/root cause) and **Test plan** (checklist) sections, ending with the attribution lines from the session reminder.

## 2. Open it
- **One PR per task/session.** Follow-up requests on the same work (more changes, tweaks, extra fixes) go on the same branch and the same PR -- update its description -- never a new branch or separate/stacked PR unless the user explicitly asks for one.
- `mcp__github__create_pull_request` (owner `JonLatane`, repo `rellm`, base `main`).
- Then `subscribe_pr_activity` so CI results, comments and reviews arrive as events -- don't poll or sleep.

## 3. CI
- `mcp__github__pull_request_read` with `get_check_runs` / `get_status`; for failures use `mcp__github__get_job_logs`.
- Fix the real cause. Never skip, disable or quarantine a test, and never push empty commits to retrigger CI.
- Commit and push the fix to the same branch.

## 4. Greptile review
- Read its feedback with `get_reviews` and `get_review_comments` (reviewer is `greptile-apps`).
- Address each valid finding in code. Don't write verbose replies to Greptile: a fixed finding needs no reply at all (the `@greptileai` re-review below is the signal); for one you decline, a single short sentence in its thread (via `add_reply_to_pull_request_comment`) saying why, ending with the footer `_Generated by [Claude Code](https://claude.ai/code)_`.
- **After pushing fixes for Greptile, post a PR comment whose entire body is `@greptileai`** -- nothing else, no explanation, no footer -- via `add_issue_comment` to request the re-review. Don't do this if nothing changed for Greptile.
- Repeat 3-4 until CI is green and Greptile has no outstanding findings. Never approve or merge.
